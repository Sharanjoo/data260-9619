## 2. Describe one thing the AI got wrong, or one thing you verified.

Several things were wrong or untrue until I ran them. (a) Every seeded `recall_record` had `units_affected = 0`, so the first record-picking script found no usable record; the data had to be fixed (32 records were given units deterministically, which the report discloses). (b) The assistant expected `qwen3:8b` to make the mistakes the Part 4 loop is supposed to learn from, but it answered all 16 first training questions correctly, so there was nothing to learn. (c) The Evaluator's list of refusal phrases was too narrow: "The recall notice does not provide information about the CEO" was scored as a made-up answer, which created false failures in training. (d) The first validation gate (accept a lesson only if it fixes a question and breaks none) rejected all three lessons because each one changed the answer to one borderline question, V06; the assistant then proposed a net-gain rule. (e) The two training runs with 16 questions produced fewer than two failures of any kind, so no lesson could be created.

## 3. How did you detect or verify it?

I saw each of these in the terminal output: the picker's "0 eligible" message, the 16/16 pass line for `qwen3:8b`, the training lines `T14` and `T16` marked as failures although the saved answers were correct refusals, the gate line "rejected" three times with the same question broken, and "lessons created: []". The saved per-question answers are in `raw/part4_train*.jsonl` and `raw/part4_validate_*.jsonl`. I kept the evidence of every attempt (the `qwen3:8b` run, both 16-question `qwen3:1.7b` runs, the strict gate result) instead of overwriting it. The test set was never used to make any of these changes (the Evaluator wording fix, the larger training set and the gate rule were all decided on training and validation results before the variants were run). I also did not trust the offline tests for Part 4, which use a scripted fake model: the results in the report come from the real runs with `qwen3:1.7b`, and the sweep results come from the real Redis index, with the agent latencies replayed from a real agent pass.

## 4. What changed, and why does it work?

The Evaluator accepts more refusal wordings and gives a more specific hint for the "what should I do" case; the training set went from 16 to 40 questions (validation and test files unchanged); the Answering Agent uses `qwen3:1.7b`; and the gate uses a net-gain rule (I kept the strict result in `raw/part4_gate_strict.json` and I say in the report that I changed the rule after seeing it). It works because a lesson is only created after the same failure pattern appears twice on training questions, it is only kept if it helps on separate validation questions, and the final comparison runs on 20 test questions that were not used before. On the test set lessons plus retry passed 20/20 against 17/20 for the baseline. Limits I want to be clear about: 20 test questions is small, the model is not exactly repeatable (V1 and V2 differ on the same question although the prompts are the same), the Evaluator is rule-based and checks only facts it was written to check, the Part 4 data is synthetic, the sweep is a replay with measured agent latencies, and even the shipped threshold 0.95 still served one wrong answer (case C23), so a similarity threshold alone is not safe for this kind of question.
